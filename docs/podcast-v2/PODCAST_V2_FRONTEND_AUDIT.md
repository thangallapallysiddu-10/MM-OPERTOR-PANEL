# Podcast V2 Frontend Audit

Current filesystem audit of the Podcast V2 frontend.

Scope:

- Frontend Podcast Studio source under `Melody_meet/OPERATOR_PANEL/src/features/podcast`
- Public guest pages used by podcast links under `Melody_meet/OPERATOR_PANEL/src/pages`
- Shared frontend services and store paths used by Podcast V2
- Backend routes/services/models referenced by the current frontend implementation

Rules applied:

- Source code only.
- No assumed functionality.
- No source code changes.

## Classification Legend

| Status | Meaning |
|---|---|
| REAL | Implemented with actual browser/native/backend behavior and actively wired. |
| PARTIAL | Some real behavior exists, but the feature is incomplete, partly local-only, or not fully connected. |
| MOCK | Uses simulated, hardcoded, random, timeout, placeholder, or fallback behavior. |
| UI ONLY | Visual/control surface exists, but no real functional implementation is wired. |
| MISSING | Expected by current UI/contracts, but no current implementation exists in source. |

## 10. Current Audio Flow

### Host Live / Guest WebRTC Flow

Status: PARTIAL

Current implementation:

1. `PodcastUpload` calls `useLiveStream`.
2. `useLiveStream` tests or starts live by acquiring host mic stream with `navigator.mediaDevices.getUserMedia({ audio: true })`.
3. `PodcastUpload` passes `liveStreamHook.mediaStream` into `usePeerConnections`.
4. `usePodcastSocket` connects the host to `/podcast` and listens for `webrtc_offer`.
5. Incoming WebRTC offers are stored as `podcast.pendingWebRtcSignal` in Zustand.
6. `usePeerConnections` reads the pending signal, creates an `RTCPeerConnection`, sets remote description, adds host mic tracks, creates an answer, and emits `webrtc_answer`.
7. When remote guest track arrives, `usePeerConnections` connects it to a per-slot `GainNode` and `AudioContext.destination`.

- `src/features/podcast/PodcastUpload.tsx`

## 15. Overall Architecture

Current Podcast V2 frontend architecture is centered on `PodcastUpload.tsx` as a single screen-level orchestrator. It combines:

- Local UI state in component state.
- Global podcast state in Zustand `useAppStore`.
- REST calls through `PodcastApi`.
- Socket.IO host-side events through `podcastSocket`.
- Browser/native audio capture through `useRecording` and `useLiveStream`.
- Host-side WebRTC audio receive through `usePeerConnections`.
- Multiple UI panels that are not connected to the real audio/backend flow.

The real host-side live/session/audio pieces are split across:

- `useLiveStream` for live metadata and host mic stream.
- `usePodcastSocket` for host socket room, chat, slot updates, and WebRTC signaling.
- `usePeerConnections` for host WebRTC answer/remote audio playback.
- `useRecording` for mic-only recording and upload.

The main architectural disconnects in current source are:

- Podcast mixer UI (`PodcastAudioDeck`) is separate from actual WebRTC audio (`usePeerConnections`).
- Master output UI (`PlayerAudioFXPanel`) is separate from actual audio output.
- Guest UI (`GuestJoinPage`, `GuestRoom`) is separate from guest APIs, socket methods, and WebRTC methods.
- Episode manager UI is separate from episode backend APIs.
- Shared audio engine services exist but are not used by Podcast V2.
